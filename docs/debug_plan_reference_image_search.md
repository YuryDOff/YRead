# План отладки поиска референсных изображений (Reference Image Search)

**Статус инструментации:** выполнена. В `search_service.py` добавлены вызовы `_debug_session_log()`; логи пишутся в `debug-7e0e1f.log` (корень проекта) в формате NDJSON.

Цель: убедиться, что (1) все выбранные пользователем движки вызываются и возвращают ненулевые результаты, (2) ответы каждого провайдера содержат метаданные для фильтрации и ранжирования, (3) итоговая выдача справедливо представляет лучшие изображения от всех движков.

---

## 1. Текущая архитектура (кратко)

- **Провайдеры:** `ALL_PROVIDERS` = unsplash, serpapi, pexels, pixabay, openverse, wikimedia, deviantart.
- **Выбор движков:** В `search_references_for_book()` список провайдеров формируется из `available_provider_names` (те, у кого `is_available()`), при наличии `enabled_providers` от пользователя — пересечение с этим списком.
- **Режим:** При `preferred_provider is None` или `"auto"` используется **агрегация** (`_search_all_providers`): для каждого запроса вызываются все выбранные провайдеры, результаты объединяются. Иначе — один провайдер на запрос (`_search_with_providers`, первый успешный).
- **Ранжирование:** `_filter_dedupe_and_rank()` использует `_alignment_score(query_text, img)`, который опирается на `img["search_metadata"]` (title, description, alt, tags). Если метаданных нет — возвращается нейтральный 0.5.
- **Метаданные по провайдерам:**
  - **Есть search_metadata:** Unsplash, Pexels, Pixabay.
  - **Нет search_metadata:** Openverse, Wikimedia, SerpAPI, DeviantArt → при ранжировании получают 0.5 и могут проигрывать провайдерам с богатыми метаданными.

## 2. Три области проверки

### 2.1 Все выбранные движки вызываются и возвращают не ноль картинок (где это возможно)

**Гипотезы для проверки:**

- **H-A:** Список `enabled_providers` с фронта не доходит или не применяется — в расчёт попадают не те провайдеры.
- **H-B:** Часть провайдеров помечается как недоступная (`is_available() == False`) из‑за отсутствующих ключей/конфигурации и пропускается.
- **H-C:** Провайдер вызывается, но возвращает 0 результатов (API пустой ответ, ошибка, таймаут) или бросает исключение — результат не попадает в агрегат.
- **H-D:** В агрегированном пуле после фильтрации остаются изображения только от одного-двух провайдеров (остальные отфильтровываются по размеру/дедупу или не попадают в топ по score).

**Инструментация (логи):**

- В `search_references_for_book`: после построения списка провайдеров логировать `available_provider_names`, `enabled_providers` (вход), `use_aggregate_providers`, `provider_names_in_use`.
- В `_search_all_providers`: для каждого провайдера — до вызова (имя), после вызова — количество возвращённых результатов; при исключении — имя и текст ошибки.
- После `_filter_dedupe_and_rank` по каждой сущности: количество картинок по полю `provider` (распределение по движкам в финальной выдаче).

**Тест (автоматический):**

- Скрипт/тест: для фиксированного `book_id` с хотя бы одним главным персонажем/локацией вызвать `search_references_for_book(..., enabled_providers=["unsplash","pexels","pixabay","openverse","wikimedia"])` (или список всех доступных по `get_providers_status()`).
- Утверждения:
  - Каждый из переданных в `enabled_providers` провайдеров, у которого `is_available() == True`, был вызван (по логам или по моку).
  - В `provider_usage` в ответе для каждого такого провайдера либо count > 0, либо явно зафиксировано в логах, что провайдер вернул 0 результатов (не ошибка).

---

### 2.2 Результаты каждого провайдера содержат метаданные для фильтрации и ранжирования

**Гипотезы:**

- **H-M1:** Часть провайдеров не заполняет `search_metadata` (или title/description/alt/tags на верхнем уровне) — их изображения всегда получают score 0.5 и не конкурируют по релевантности.
- **H-M2:** Формат метаданных от API отличается от ожидаемого (другие ключи, вложенность) — парсер не кладёт данные в `search_metadata`.

**Что нужно для ранжирования:**

- В `_alignment_score` используются: `search_metadata.title`, `search_metadata.description`, `search_metadata.alt`, `search_metadata.tags` (base.py: опционально те же поля на верхнем уровне). Плюс для фильтрации: `url`, `width`, `height` (min_size), `provider`.

**Инструментация:**

- В каждом провайдере при добавлении элемента в `results`: логировать (выборочно, например первый и последний результат) наличие и непустоту `search_metadata` или эквивалентных полей.
- В `_filter_dedupe_and_rank`: перед сортировкой можно логировать долю изображений с непустым `search_metadata` и по `provider` (сколько от каждого провайдера имеют метаданные).

**Тест (автоматический):**

- Юнит-тесты для каждого провайдера (или интеграционный тест с моком HTTP): вызвать `provider.search(query, content_type, count=5)`, для каждого элемента результата проверить:
  - Есть ключи: `url`, `provider`, `width`, `height`.
  - Для ранжирования: либо есть `search_metadata` (dict с хотя бы одним непустым из title/description/alt/tags), либо документированное решение, что провайдер не даёт метаданных (тогда ожидаем 0.5 в `_alignment_score`).
- Регрессионный тест: `_alignment_score` на примерах с заполненным и пустым `search_metadata` (уже есть в `test_search_filter_rank.py`).

---

### 2.3 Итоговая выдача справедливо представляет лучшие изображения от всех движков

**Гипотезы:**

- **H-F1:** Ранжирование только по `relevance_score` без квот по провайдерам — один движок с богатыми метаданными заполняет весь топ, остальные почти не видны.
- **H-F2:** Дедуп по домену в старом `_filter_and_dedupe` с `prefer_unsplash` даёт приоритет Unsplash при конфликте доменов (в текущем коде используется `_filter_dedupe_and_rank`, но стоит проверить, не вызывается ли где-то старая логика).
- **H-F3:** Жёсткий фильтр по размеру (min_size 512) отсекает много результатов отдельных провайдеров, у которых по умолчанию приходят маленькие превью.

**Инструментация:**

- После `_filter_dedupe_and_rank` по каждой сущности: подсчёт и логирование распределения по `provider` в финальном списке (например, `{ "unsplash": 35, "pexels": 10, "pixabay": 5 }`).
- Опционально: распределение по провайдерам до ранжирования (по всем `all_images`) и после — чтобы видеть, теряется ли разнообразие на этапе ранжирования.

**Критерий «справедливо» (для теста/метрики):**

- Если провайдеры A, B, C каждый вернул хотя бы N результатов (например N ≥ 5), в топ-50 финальной выдачи каждый из A, B, C должен быть представлен хотя бы минимальным числом картинок (например не 0). Порог можно задать конфигурируемо (например, не более 90% от одного провайдера в топ-20).

**Тест (автоматический или ручной сценарий):**

- Запуск поиска с 3–4 провайдерами, у которых есть метаданные (Unsplash, Pexels, Pixabay) и 1–2 без метаданных (Openverse, Wikimedia).
- Проверка по логам/ответу API: в `provider_usage` все выбранные провайдеры дали хотя бы по одному результату в агрегате; в финальных `images` по сущности — не один провайдер не занимает, например, 100% топ-20 (при наличии данных от нескольких).

## 3. План внедрения (по шагам)

### Шаг 1: Логирование (без изменения поведения)

- **search_service.py**
  - В `search_references_for_book`: оставить/добавить лог с `available_provider_names`, `enabled_providers`, `use_aggregate_providers`, `provider_names_in_use` (hypothesisId: H-A, H-B).
  - В `_search_all_providers`: для каждого провайдера лог «вызван»/«пропущен (not available)»/«вернул N результатов»/«исключение» (H-C).
  - В `_search_entity` после `_filter_dedupe_and_rank`: лог распределения по `provider` в `filtered` (H-D, H-F1).
- **Провайдеры (опционально):** при первом/последнем результате в `results` логировать наличие `search_metadata` (H-M1, H-M2). Можно централизованно в `search_service`: после сбора `all_results` пройтись и залогировать долю с метаданными по провайдеру.

Использовать единый debug-лог (например NDJSON в файл или существующий механизм) с полями: `sessionId`, `hypothesisId`, `message`, `data`, `timestamp`.

### Шаг 2: Скрипт/тест «все движки вызываются»

- **Вариант A — интеграционный тест (pytest):**  
  Использовать реальную БД и книгу с главным персонажем. Вызвать `search_references_for_book(book_id, search_all=False, enabled_providers=[...])` со списком всех доступных провайдеров. По ответу и логам проверить: каждый доступный провайдер из `enabled_providers` присутствует в логах как вызванный и либо дал count > 0 в `provider_usage`, либо в логах есть «returned 0 results».
- **Вариант B — отдельный скрипт (реализован):**  
  `backend/scripts/run_reference_search_debug.py`: загрузка окружения, получение списка доступных провайдеров, один вызов `search_references_for_book` с переданным `book_id` и `enabled_providers=list(available)`. Запуск из каталога `backend`: `python -m scripts.run_reference_search_debug <book_id>`.

### Шаг 3: Проверка метаданных провайдеров

- В тестах провайдеров (`test_search_providers.py` или новый файл) для каждого провайдера: мок ответа API → `provider.search(...)` → проверка структуры каждого элемента (url, provider, width, height; при наличии API-полей для текста — что они маппятся в `search_metadata`).
- Документировать в коде или в этом плане: какие провайдеры не отдают метаданные (Openverse, Wikimedia, SerpAPI, DeviantArt) и что для них ожидается score 0.5. При желании позже добавить в эти провайдеры парсинг title/description из API, если он есть.

### Шаг 4: Анализ «справедливости» выдачи

- По логам из шага 1 (распределение по `provider` в `filtered`) проверить на реальном запуске: есть ли движки с 0 картинок в топ-50 при том, что в `provider_usage` они дали ненулевой вклад. Если да — рассмотреть доработку ранжирования (например, квота по провайдерам в топ-N или отдельный «diversity by provider» шаг после score).

### Шаг 5: Воспроизведение пользователем и сбор логов

- Инструкция пользователю: включить в настройках нужные движки (Settings → провайдеры), на странице Review Search запустить поиск референсов, после завершения прислать или открыть лог-файл сессии.
- По логам проверить H-A–H-D, H-M1–H-M2, H-F1–H-F3 и зафиксировать выводы (подтверждено/опровергнуто).

В выводе проверьте:

## 7. Ручная проверка движков (manual verification)

Чтобы понять, возвращают ли Pixabay / Openverse / Wikimedia пустой результат из‑за **технической ошибки** или из‑за **отсутствия контента** по вашему запросу, можно подставить тот же поисковый запрос в веб-интерфейс каждого движка.

### Откуда взять поисковую строку

- **В приложении:** страница **Review Search** (Search Queries) — там отображаются предложенные запросы по каждому персонажу/локации. Скопируйте нужную строку из списка запросов по сущности (например, для Razoumikhin).
- **Через API:** `GET /books/{book_id}/proposed-search-queries` — в ответе по каждой сущности будет список `queries`; можно использовать любой из них.
- **После прогона поиска:** запросы сохраняются в БД в таблице `search_queries` (поле `query_text`).

### Куда подставлять строку вручную

Подставьте вашу строку вместо `YOUR_SEARCH_QUERY` (пробелы в URL будут закодированы как `%20`; в браузере можно вводить фразу с пробелами — адресная строка подставит кодировку).

| Движок | Поиск в браузере (подставьте вместо `YOUR_SEARCH_QUERY`) |
|--------|------------------------------------------------------------------|
| **Pixabay** | https://pixabay.com/images/search/**YOUR_SEARCH_QUERY**/ — на сайте можно ввести фразу с пробелами (в URL они станут `-` или `+`). В API приложение отправляет слова через `+` (например `man+portrait+fiction`). |
| **Openverse** | https://openverse.org/search/?q=**YOUR_SEARCH_QUERY** — запрос передаётся как есть (пробелы → `%20`). |
| **Wikimedia Commons** | https://commons.wikimedia.org/wiki/Special:Search?search=**YOUR_SEARCH_QUERY** — в приложении к запросу добавляется префикс `filetype:bitmap`; для ручной проверки можно искать просто по фразе или добавить `filetype:bitmap` в начало. |

### Как интерпретировать результат

- **В вебе есть картинки по этой фразе, а в приложении провайдер даёт 0** → вероятна техническая причина (формат запроса, лимиты, ключ, User-Agent и т.д.).
- **В вебе тоже пусто** → по этой конкретной фразе у движка нет подходящего контента; можно попробовать укороченный или более общий запрос (например, первые 3–4 слова).
