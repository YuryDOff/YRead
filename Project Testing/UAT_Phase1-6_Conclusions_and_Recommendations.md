# UAT Phase 1–6: выводы и рекомендации

**Источник:** таблица результатов UAT + `implementation_plan 4.0.md`.

---

## 1. Тесты 17, 18, 19, 20, 21 (и 22) — должны ли были выполняться после фазы 6?

**Ответ: да.** По плану реализации 4.0 эти тесты относятся к объёму **фазы 6**.

В плане явно указано:

| Раздел плана | Содержание |
|--------------|------------|
| **6.2** | Расширение `search_references_for_book` на типы сущностей `artefacts` и `cover`. |
| **6.3** | Расширение `get_proposed_search_queries`: возвращать `artefacts` и `cover` (в т.ч. `proposed_queries` для обложки). |
| **6.4** | Расширение `GET reference-results`: включить `artefacts` и `cover`; расширение `POST visual-bible/approve`: `artefact_selections`, `cover_selections`; расширение `reference-upload` для `entity_type = "artefact" \| "cover"`. |

То есть проверки:

- **17** — предложенные поисковые запросы включают артефакты и обложку;
- **18** — референсный поиск только для артефактов;
- **19** — референсный поиск только для обложки;
- **20** — результаты референсного поиска возвращают артефакты и обложку;
- **21** — утверждение с выбором артефактов и обложек;
- **22** — загрузка референсов для артефактов и обложки;

по плану входят в фазу 6 и **корректно назначены на «после фазы 6»**.

Фактические провалы UAT означают, что **реализация фазы 6 не завершена**, в первую очередь на фронтенде, а не то, что тесты запланированы на «более позднюю фазу».

**Проверка кода:**

- Бэкенд: `reference-results` уже возвращает `artefacts` и `cover`; `visual-bible/approve` принимает `artefact_selections` и `cover_selections`; `search_service` поддерживает `search_entity_types` с `artefacts` и `cover`; `get_proposed_search_queries` формирует данные по артефактам и обложке.
- Фронтенд: на странице поисковых запросов отображаются только персонажи, локации и сцены; в `api.ts` тип `search_entity_types` ограничен `'characters' | 'locations' | 'both'`; `approveVisualBible` и типы не учитывают артефакты/обложку; нет UI для выбора референсов по артефактам/обложке и для загрузки референсов по ним.

**Рекомендация:** не переносить тесты 17–22 на более позднюю фазу; довести до конца реализацию фазы 6, в первую очередь фронтенд (страница поисковых запросов, типы API, экран утверждения Visual Bible, загрузка референсов).

## 2. Рекомендации по исправлению провалившихся тестов

### Сценарий 1 (Фаза 1) — Книга хранит жанр и активации сущностей

**Наблюдения:** `is_well_known = 0`, не заполняются `well_known_author` / `well_known_book_title`, не заполняется жанр, нет контроля для типов рабочего процесса (Full / Title).

**Рекомендации:**

1. **Жанр:** при создании книги из формы загрузки жанр передаётся только в метаданные и в контекст (style_category). В запрос `POST /books/{id}/analyze` и при обновлении книги нужно передавать и сохранять `genre` (например, из контекста/метаданных загрузки или из шага «Ключевые параметры») и вызывать `update_book(..., genre=...)`.
2. **Well-known книга:** при анализе уже передаются `is_well_known`, `well_known_book_title`, `author` и сохраняются в `update_book` в начале анализа. Стоит проверить: что форма «Известная книга» действительно вызывает анализ после заполнения; что в ответе `GET /books/{id}` возвращаются поля `is_well_known`, `well_known_book_title`, `author` (и при необходимости добавить их в схему ответа).
3. **Тип рабочего процесса (Full / Cover only):** в модели есть `workflow_type` (`full` / `cover_only`). Добавить в UI (например, на шаге загрузки или ключевых параметров) выбор «Полная книга» / «Только обложка» и при создании или обновлении книги передавать и сохранять `workflow_type`.

---

### Сценарий 5 (Фаза 2) — Связи артефакт–фрагмент–сцена

**Наблюдения:** в `scene_artefacts` 0 записей; в `scene_locations` только одна запись; в таблице сцен есть пустые сцены (без названия и narrative summary).

**Рекомендации:**

1. **Scene–artefact:** логика `link_scene_artefact` уже вызывается из фонового анализа в `books.py`. Убедиться, что после анализа артефактов для каждой сцены вызывается привязка артефактов к сценам (по совпадению фрагментов/сцен с теми фрагментами, где артефакт упоминается). При необходимости добавить явное построение связей сцена–артефакт после `run_artefact_analysis`.
2. **Scene–locations:** проверить экстрактор сцен и сохранение связей сцен с локациями: привязка локаций к сценам должна быть по тем же правилам, что и для персонажей (например, по упоминаниям в summary сцены).
3. **Пустые сцены:** в экстракторе сцен не создавать сцены без `title` и `narrative_summary`, либо фильтровать их при сохранении, либо помечать как «черновик» и не показывать в основных списках до заполнения.

---

### Сценарий 11 (Фаза 5) — Выборочный анализ по типам сущностей

**Наблюдение:** функция выборочного анализа недоступна в интерфейсе.

**Рекомендация:** бэкенд уже принимает `entity_types` в `POST /books/{id}/analyze`. На шаге «Ключевые параметры» (или отдельном шаге перед запуском анализа) добавить выбор типов сущностей: чекбоксы или мультиселект для «Обложка», «Персонажи», «Локации», «Артефакты» и передавать выбранный список в запросе анализа как `entity_types`.

---

### Сценарий 12 (Фаза 5) — Прогресс анализа по сущностям

**Наблюдение:** экран прогресса монотонный, не показывает прогресс по сущностям.

**Рекомендация:** бэкенд уже отдаёт в `GET /books/{id}/analysis-progress` структуру с `entity_progress` (по типам сущностей). На экране «Анализ выполняется» отображать статус по каждому типу (например, «Персонажи: 15/20», «Локации: готово», «Артефакты: в процессе», «Обложка: ожидание») на основе `progress.entity_progress` и обновлять при опросе прогресса.

---

### Сценарий 13 (Фаза 5) — Повторный запуск анализа для одного типа сущностей

**Наблюдение:** функция недоступна в приложении.

**Рекомендация:** эндпоинт `POST /books/{id}/analyze/entity` с телом `{ "entity_type": "artefacts" }` уже реализован. В UI (например, на странице обзора анализа или в карточке книги) добавить кнопки/действия вида «Перезапустить анализ: персонажи», «…локации», «…артефакты», «…обложка», вызывающие этот эндпоинт с нужным `entity_type`.

### Сценарии 17–22 (Фаза 6) — Поиск и утверждение для артефактов и обложки

**Общее:** бэкенд в основном готов (поиск, предложенные запросы, reference-results, approve с artefact/cover). Провалы связаны с отсутствием поддержки на фронтенде.

**Рекомендации:**

| Тест | Что сделать |
|------|-------------|
| **17** | На странице предложенных поисковых запросов показывать блоки «Артефакты» и «Обложка» (как для персонажей/локаций), используя ответ `get_proposed_search_queries` с полями `artefacts` и `cover`. |
| **18, 19** | В `api.ts` расширить тип `search_entity_types` до `'characters' | 'locations' | 'both' | 'artefacts' | 'cover' | 'all'`. В UI страницы поиска добавить опции «Только артефакты», «Только обложка» (и при необходимости «Все») и передавать выбранное значение в запрос поиска. |
| **20** | Тип `ReferenceImages` и отображение на странице результатов референсов расширить: показывать секции «Артефакты» и «Обложка» по данным `reference-results` (уже приходят в ответе). |
| **21** | В `api.ts` расширить вызов `approveVisualBible`: принимать и отправлять `artefact_selections` и `cover_selections`. В компоненте утверждения Visual Bible (например, `VisualBibleReview`) добавить вкладки/секции для артефактов и обложки и возможность выбирать референсы для них, затем передавать в approve. |
| **22** | Реализовать в UI загрузку референсного изображения для сущности с типом `artefact` и для обложки (`cover`); бэкенд `reference-upload` при необходимости расширить для `entity_type = "artefact" | "cover"` (если ещё не поддерживается). |
